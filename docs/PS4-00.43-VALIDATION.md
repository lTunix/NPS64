# Local diagnostic 00.43: Tennis replay GPU stages

## Result from physical 00.42

The user reports that slowdowns persist during Mario Tennis replays. Fresh logs
show an interval at 25.85 VI/s against 50.01, with 29.169 ms mean RDP time and
an 88.933 ms RDP peak. Several other replay intervals fall to 35–42 VI/s.
Shader demand prioritization is not sufficient to resolve the slowdown.

The log includes 187 shader queue starts; the largest wait is 17,864.218 ms.
Recent-demand prioritization can delay less recently used jobs, so this maximum
must not be presented as a queue-wait improvement. GPU stage measurements are
needed rather than another assumption about compiler scheduling.

## Diagnostic change

`--stage-timings` enables the renderer's existing timestamp profiler via
`PARALLEL_RDP_BENCH=2`. The frontend reports stages once per performance interval:
span setup, tile binning, TMEM updates, shading, depth blending, native and
upscaled render passes, and VI processing. The report and reset use the device
mutex also used by compiler interval publication and frame recycling.

Stage values are GPU timestamp intervals per frame context and per invocation,
with invocation counts. Render-pass records contain component stages; do not
sum the enclosing records and their components. Native and upscaled render-pass
records are distinct. Startup/compilation and partially completed frame contexts
can affect early windows; compare the steady replay interval with normal play.

This package measures the workload and can add overhead. Its FPS is not an
optimization benchmark. Shaders, quality, resolution, FullSync and the resource
guards remain unchanged. The build rejects combining `--stage-timings` with
`--public-release`.
