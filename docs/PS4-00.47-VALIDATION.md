# Local optimization 00.47: 2D active tile dispatches and fast masked readback copy

## Physical baseline (00.46)

In physical PS4 testing of `00.46` (`Mario Tennis (E) (VC).z64` at 2x resolution,
PAL target ~50.01 VI/s), the median gameplay cadence reached 49.74 FPS (101 of
113 gameplay intervals >= 48 FPS), confirming that `00.46` submission batching
and indirect-reset skipping were active. However, particle-heavy replays and ball
trails still dropped to **31.42–33.90 FPS** (`rdp_ms=21.939 / 20.500 ms`, peaks
`60.842 / 64.406 ms`).

Comparing the 00.46 PS4 logs between normal gameplay (`frames=1531`, `50.67 FPS`,
`rdp_ms=8.317 ms`) and the worst interval (`frames=1445`, `31.42 FPS`,
`rdp_ms=21.939 ms`):

- `processed_pixels` barely changed (`45.9M` vs `54.4M`, +18%), and `triangles`
  was actually 25% lower (`26,295` vs `19,723`).
- In contrast, `full_pixels` (`fb.width * fb.deduced_height` summed across the
  3,425 passes caused by 2,843 texture hazards and 552 framebuffer switches)
  jumped **2.5x–2.9x** (`133.4M` -> `331.5M / 382.9M`), where active rows
  represented only **16.4%** of `full_pixels`.
- In `00.45`–`00.46`, only `submit_update_upscaled_domain` (`Pre`/`Post`) was
  bounded to active rows. `submit_depth_blend` (`6.24 ms/frame` in 00.43) and
  `submit_tile_binning_combined` (`4.20 ms/frame` in 00.43) still dispatched
  compute workgroups across the entire `[0 .. fb.width) x [0 .. fb.deduced_height)`
  (`full_pixels`) on every native and 2x pass.
- In addition, `masked_memcpy` in `rdp_device.cpp` (executed on `timeline_worker`
  and blocking `FullSync`) unconditionally issued microcoded non-temporal
  `_mm_maskmoveu_si128` (`MASKMOVDQU`) on every 16-byte chunk of every readback
  page (~117 MB/s during slow intervals), even when the byte mask was all-zero
  (`0x0000`) or all-ones (`0xffff`).

## Changes included in 00.47

- **2D active tile and meta-tile bounding via `vkCmdDispatchBase`**:
  - Extended `src/rdp_update_window.h` with `nps64_rdp_interp_x` (matching the
    exact 32-bit signed saturation before `>> 15` in `shaders/binning.h`),
    `nps64_rdp_primitive_x_bounds_scaled`, `nps64_rdp_accumulate_x_bounds`, and
    `nps64_rdp_tile_window`.
  - Added `CommandBuffer::dispatch_base` in `vulkan/command_buffer.hpp` and
    `vulkan/command_buffer.cpp` (with `VK_PIPELINE_CREATE_DISPATCH_BASE` on
    compute pipelines to satisfy `VUID-vkCmdDispatchBase-baseGroupX-00427`).
    Verified in the PS4 RADV driver (`radv_cmd_buffer.c`) that `radv_CmdDispatchBase`
    programs hardware `R_00B810_COMPUTE_START_X/Y/Z` on GFX7/PS4 and restores
    `S_00B800_FORCE_START_AT_000(1)` on normal dispatches.
  - Bounded `Renderer::submit_tile_binning_combined` (64x32 meta-tiles, 1x and 2x)
    and `Renderer::submit_depth_blend` (8x4 tiles, 1x and 2x) to the 2D active
    tile window `[base_tile_x .. end_tile_x) x [base_tile_y .. end_tile_y)` of
    each pass. Since both shaders depend only on `gl_WorkGroupID.xy` and
    `gl_GlobalInvocationID.xy`, offsetting the workgroup start coordinates via
    `vkCmdDispatchBase` requires zero shader/SPIR-V modifications.
  - Added `full_blend_tiles`, `active_blend_tiles`, `full_bin_groups`, and
    `active_bin_groups` counters to `[rdp-active-rows]`.
    `NPS64_RDP_REFERENCE_TILES=1` selects the unclipped `00.46` dispatch path.
- **Fast SSE2 readback `nps64_fast_masked_memcpy` in `rdp_device.cpp`**:
  - Inspects `_mm_movemask_epi8(mask)` per 16-byte chunk: skips `bits == 0`
    completely, uses a normal cached `_mm_storeu_si128` store when
    `bits == 0xffff`, and falls back to `_mm_maskmoveu_si128` only on partial
    boundary chunks.

No shader code, graphics quality, particles, resolution, audio, command ordering,
FullSync barriers, or resource guards were modified.

## Changes rejected before packaging

Two experimental coherency optimizations were tested and rejected during local
equivalence verification:

1. Deduplicating `page_to_masked_copy` across passes within the same command
   buffer (`coh_dedup`): produced 4 frame hash mismatches (frames 182–185)
   because `CommandProcessor::ring` runs asynchronously to the CPU thread, which
   can write to `host_rdram` between two batches coalesced into the same
   `stream.cmd`.
2. Restricting `mark_pages_for_gpu_read` in `flush_queues` to the active Y
   window and aliasing `window.depth = window.color` when `!fb.depth_read_pending`
   (`coh_window`): produced 2 frame hash mismatches (frames 138–139) because CPU
   writes to `host_rdram` outside `window.color` rely on `flush_queues` marking
   `[0 .. fb.deduced_height)` for upload, and 1x offscreen passes without `Post`
   rely on subsequent `Pre` passes to synchronize `vram_reference16`.

Both coherency experiments were completely removed from
`scripts/patch_rdp_active_rows.py` and are absent from the final core and PKG.

## Local validation

- **Unit and oracle verification (`tests/test_rdp_update_window.c`)**:
  - 239,303 active-row windows and **2,520,320** 2D tile-binning oracle checks
    against an exact C implementation of `shaders/binning.h:bin_primitive()`
    pass with 0 mismatches under ASan/UBSan.
- **Deterministic Mario Tennis state replay (`build/corrections-00.74/active-tiles-validation.json`)**:
  - All **259 consecutive readback frames** from `batch-tuning-final.log` (`00.46`
    reference) match `active-tiles-final.log` (`00.47`) bit-for-bit
    (`image_mismatches: 0`).
  - Zero ASan memory errors and zero `VK_LAYER_KHRONOS_validation` errors.
  - At the common 240-image reporting boundary (`SUBMIT_AT_FRAME 240`), both runs
    execute the exact same `3,005` native passes, `2,542` upscaled passes,
    `110,779` primitives, `2,542` paired passes, and `67` skipped indirect resets.
  - Across those 240 frames, 8x4 depth-blend tile workgroups drop from
    `12,168,456` to `4,450,254` (**63.43% reduction**, `7,718,202` tile groups
    skipped), and 64x32 tile-binning workgroups drop from `871,424` to `596,966`
    (**31.50% reduction**, `274,458` binning groups skipped). In particle-heavy
    windows (frames 120–140), blend tile dispatches drop by **57.72%** overall
    (and up to **81.97%** in the heaviest 20-frame sub-interval, `533,008` ->
    `96,099`).
  - These work-reduction percentages are native Vulkan work-count measurements,
    not a claim of an equivalent PS4 FPS percentage gain.
